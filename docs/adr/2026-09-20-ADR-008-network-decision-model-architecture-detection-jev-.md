# ADR-008: Network + decision-model architecture detection (Jev System One)
- **Date:** 2026-09-20 14:41:24
- **Status:** active
- **Context:** Until now the watcher was strictly static, import-graph-only, and AGENTS.md hard-ruled "never touch network or an LLM". The user asked whether the plugin could determine VSA-vs-other-architectures and whether it could be modular for any architecture.
- **Decision:** Add an opt-in `archdetect` slice that calls the TypeSafe Jev decision model (`~typesafe/jev-latest` → `typesafe/jev-1.13`) over OpenRouter's `/api/v1/systemone` endpoint. Jev is a `text->decisions` model, so it is queried with a single typed `choice` question (not chat). Gated behind `detectArchitecture` (default false) so the zero-network default is preserved; `/vsa detect` runs it and persists the chosen `architecture`. Architecture set is an archetype registry (vsa/clean/hexagonal/layered/modular-monolith/fsd) in `src/slices/archdetect/archetypes.ts`. Auth via `OPENROUTER_API_KEY` env var (never stored in `.pi/architecture-watcher.json`).
- **Consequences:** AGENTS.md "no network" rule is now conditional: detection is opt-in and off by default. The `archdetect` slice is the only network-touching code (isolated in `systemone.ts`, fetch injectable for tests). Fully modular drift *rules* per-architecture are still future work — today the registry selects the architecture label and topology mapping hints, while `classify` rules remain VSA-specific. Deep/shallow modules are deliberately **not** a model question: it is a per-module property a single global judgment cannot answer, so it stays a static heuristic (`estimateDepth`, interface-signals vs LOC) kept separate from the model path.
